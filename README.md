# Hookahton

Личный список задач с регистрацией по email. У каждой задачи есть название, описание, время создания и отметка о выполнении.

## Запуск

Нужен Docker с Compose. Из корня репозитория:

```sh
docker compose up --build
```

Откройте http://localhost:8080. Порт можно задать в `.env`. Compose применяет миграцию при запуске и хранит данные PostgreSQL в Docker-томе. Конфигурация с HTTP и демонстрационными настройками базы предназначена для локального запуска.

- `backend/` — Node.js **22.x**, TypeScript, Prisma и PostgreSQL.
- `frontend/` — Node.js **22.x** для сборки, React, TypeScript, Vite и Tailwind CSS.

Проверка API в запущенном Docker:

```sh
docker compose exec backend npm test
```

Проверка ограничения попыток входа через Nginx (только в отдельном тестовом окружении):

```sh
docker compose up -d --force-recreate frontend
docker compose exec -e PROXY_BASE_URL=http://frontend backend npm test
```

Тест намеренно исчерпывает лимит своего IP. Пересоздание тестового frontend перед повторным запуском сбрасывает этот лимит.

Frontend проверяет структуру ответов API перед отображением. Повреждённый ответ вызывает ошибку с возможностью повтора вместо пустого экрана. Тесты клиента: `cd frontend && npm ci && npm test`; проверка типов и сборка: `npm run build`.

Вход и регистрация делят лимит по IP: 5 запросов в минуту с кратковременным запасом в 10 запросов. При превышении Nginx возвращает JSON с HTTP 429 и `Retry-After`. Лимит действует только при доступе через Nginx; при локальной разработке через Vite его нет. За дополнительным reverse proxy потребуется отдельно настроить доверенные адреса, иначе клиенты будут делить IP и лимит прокси.

## Список задач и пагинация

Интерфейс загружает по 20 задач, показывает номер страницы и общее количество. После создания открывается первая страница, после удаления обновляется текущая. Пустая последняя страница автоматически заменяется последней существующей.

`GET /api/tasks?page=1&pageSize=20` возвращает:

```json
{"items": [], "page": 1, "pageSize": 20, "total": 0, "totalPages": 1}
```

`page` — положительное безопасное целое число; `pageSize` — целое от 1 до 100. Значения по умолчанию: 1 и 20. Неверные или повторяющиеся параметры возвращают HTTP 400. Слишком большой номер страницы приводится к последней существующей; для пустого списка используется страница 1 из 1. Ответ и количество включают только задачи текущего пользователя.

Сортировка: сначала новые задачи (`createdAt DESC`), при одинаковом времени — `id DESC`. Количество и содержимое страницы читаются в одной транзакции с единым снимком данных. Используется обычная offset-пагинация Prisma без новых зависимостей и изменения схемы. Для небольшого личного списка этого достаточно; если появятся очень большие списки и глубокие переходы, следует измерить запросы и рассмотреть cursor-пагинацию.

**Изменение контракта:** раньше `GET /api/tasks` возвращал массив всех задач; теперь он всегда возвращает объект страницы и ограничивает выборку. Frontend и backend нужно обновлять вместе; сторонние клиенты должны читать `items` и запрашивать следующие страницы.

## Ограничения

Авторизация использует JWT (HS256, библиотека `jose`) в HttpOnly/SameSite=Strict cookie. Срок — 7 дней. Сервер проверяет подпись, `iss`, `aud`, `sub`, `jti`, `iat`, `exp` и активную сессию в БД; в БД хранится только SHA-256 токена. Это позволяет немедленно отзывать JWT при выходе. Токен не передаётся в JSON и не хранится в localStorage; контракт frontend не меняется.

`JWT_SECRET` обязателен: 64 шестнадцатеричных символа (32 случайных байта). Без корректного ключа backend не запускается. В проектном `.env` настроен ключ для локального запуска; для публичного окружения нужен отдельный секрет. Смена ключа аннулирует все выданные JWT. Старые непрозрачные токены больше не принимаются: после обновления нужно войти заново. Миграция БД не требуется.

При успешном входе или регистрации прежняя сессия этого браузера отзывается в той же транзакции, что создаёт новую. Сессии других устройств сохраняются; неудачный вход или регистрация не разлогинивают пользователя.

Для HTTPS можно задать `COOKIE_SECURE=true` в окружении backend: cookie получает имя `__Host-session` и флаг `Secure`, а разрешённые origins localhost/127.0.0.1 используют HTTPS и `APP_PORT` (внешний порт). По умолчанию сохраняется локальный HTTP-режим. Режимы используют разные cookie; сессии другого режима сохраняются до отзыва или истечения срока. Эта опция не настраивает TLS: HTTPS-прокси необходимо подготовить отдельно.

При SIGTERM/SIGINT сервер прекращает принимать соединения, завершает текущие запросы и закрывает соединения с БД. Ожидание ограничено пятью секундами, после чего процесс завершается с ошибкой.

Задачи хранятся на сервере и доступны после входа. Синхронизации между вкладками в реальном времени, восстановления пароля и подтверждения email пока нет. Добавление или удаление задач в другой вкладке может сдвинуть границы страниц между запросами. Истёкшие сессии пользователя очищаются при его следующем входе; для постоянной эксплуатации нужна отдельная политика очистки. Перед публичным размещением также необходимы HTTPS, Secure-cookie и конфигурация разрешённого origin: текущий сервер принимает браузерные изменения только с localhost/127.0.0.1 на `APP_PORT`.
